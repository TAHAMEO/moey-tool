# Security

CLIPFORGE holds things worth protecting: OAuth tokens that can publish to your channels, AI API
keys that cost money, and your media. This document describes the threat model, the controls
that exist, and how to operate them. Report vulnerabilities privately to the repository owner.

## Threat model (summary)

| Threat | Main controls |
|---|---|
| Stolen database or backup | Secrets encrypted with AES-256-GCM under a master key that is never stored in the database or backups |
| Malicious media file (decoder exploits) | Decoding only in the media worker, which holds no secrets; FFmpeg restricted to local files and a container whitelist; size, duration and type limits |
| Prompt injection via titles, transcripts, comments, web pages | Untrusted text is fenced and labelled; the model is told it is data; injection patterns are flagged; actions need explicit user intent and role checks |
| Server-side request forgery via pasted links | Scheme allow-list, DNS resolution + private/metadata address blocking, IP pinning, manual redirect re-validation |
| Account takeover of the web app | Argon2id passwords, lockout, HttpOnly/SameSite cookies, per-session CSRF tokens, roles, audit log |
| Runaway spending or unwanted posts | Approval-first publishing, daily/monthly/per-video AI budgets, publishing limits, pause, emergency stop, per-integration switches |
| Supply chain | Pinned lock files (hash-checked for the WhisperX environment), SBOM, vulnerability audits, no AGPL code in the core |

## Secrets

- **Encryption:** every API key and OAuth token is encrypted with AES-256-GCM and a random nonce.
  The associated data binds each ciphertext to its database row and purpose, so a ciphertext
  copied into another row fails authentication.
- **Master key:** 32 random bytes in `CLIPFORGE_MASTER_KEY` (generated by `scripts/install.sh`
  or `clipforge gen-key`). It lives only in `.env` / the environment of the API and the main
  worker. Production refuses to start the API without it. Keep an offline copy: without it,
  stored credentials cannot be recovered (you would reconnect accounts and re-enter keys).
- **Rotation:** set the new key in `CLIPFORGE_MASTER_KEY`, move the old one to
  `CLIPFORGE_MASTER_KEY_PREVIOUS`, restart, run `docker compose exec worker clipforge rotate-secrets`,
  then remove the previous key when it reports `0 still use a previous key`.
- **Never exposed:** API responses show only the last four characters of a key; key, token and
  password fields are redacted from audit-log entries and are never logged by CLIPFORGE.
  Social-account passwords are never seen: you sign in on
  Google's or Instagram's own pages (OAuth with PKCE for Google; single-use, user-bound,
  15-minute `state` values).
- **Isolation:** the media worker container receives no master key, no platform secrets and
  cannot decrypt anything (`SecretsUnavailable`). The images contain no secrets; `.env` is
  excluded from the build context. Build-time proxy certificates are used only in builder stages.
- **OAuth apps** (Google client, Instagram app) saved through *Settings → Accounts* are stored
  like API keys (AES-256-GCM, admin-only, audit-logged). A copy can also have them built in
  (`config/oauth-apps.json`, mounted read-only, git-ignored): a Google *Desktop app* secret is not
  confidential by design, but a Meta app secret is — see [ONE_CLICK_CONNECT.md](ONE_CLICK_CONNECT.md)
  before shipping one. A saved Google client is checked with Google before it is kept.
- **Sign-in returns:** a Desktop-app client returns only to the loopback address the browser used
  (`http://localhost`/`127.0.0.1`, validated); the Instagram relay page
  (`deploy/oauth-relay/instagram.html`) is static, sends no referrer, has a hash-pinned
  Content-Security-Policy and forwards only to `localhost`/`127.0.0.1` on a port named in the
  CLIPFORGE-issued `state` — anything else is refused (tested in Chromium). The `state` stays
  single-use, user-bound and short-lived.

## Untrusted content

Video titles, descriptions, captions, transcripts, comments, uploaded file names and fetched web
content are treated as **data**:

- inserted into prompts only inside labelled fences, with a guard instruction that content inside
  them cannot change instructions or permissions;
- scanned for injection signals (e.g. "ignore previous instructions") every time they are placed in
  a prompt; matches are logged as warnings;
- never used to choose actions: actions come from the user's own message, are checked against the
  user's role, and anything outward-facing (publishing) needs approval unless the owner chose
  automatic publishing.

## Network fetching (SSRF)

See [SOURCE_ACCESS.md](SOURCE_ACCESS.md#safety-rules-applied-to-every-fetch). Private, loopback,
link-local and cloud-metadata addresses are refused for user-supplied links; the checked IP is
pinned for the connection; each redirect hop is re-validated; downloads are size- and type-limited.
AI provider endpoints may point at local servers (Ollama) but never at link-local or metadata
addresses. `CLIPFORGE_SSRF_PRIVATE_ALLOWLIST` exists for development only.

## Web application

- Passwords: Argon2id, minimum 10 characters with strength checks; changing a password signs out
  the other sessions.
- Sessions: random tokens stored hashed; cookie `HttpOnly`, `SameSite=Lax`, `Secure` in
  production; every state-changing request needs the per-session `x-csrf-token` header.
- Lockout: 8 failed logins per account (and 40 per client address) lock sign-in temporarily.
  Client addresses come only from the configured number of trusted proxy hops
  (`CLIPFORGE_TRUSTED_PROXY_HOPS`, 1 for the bundled Caddy) — forged `X-Forwarded-For` values are ignored.
- Roles: *viewer* (read-only), *editor* (process, edit, publish), *admin* (connections, settings,
  spending, controls), *owner* (users, delete-all-data).
- Headers: strict Content-Security-Policy, `X-Frame-Options: DENY`, `nosniff`, no referrer leakage;
  OpenAPI docs are disabled in production.
- Audit log (Settings → Account & security): sign-ins, failed sign-ins, setting changes, connections,
  publishing, data export and deletion, credential views.

## Media handling

- Uploads: extension allow-list, signature check (must really be audio/video/PNG), size limits,
  de-duplication by SHA-256; temporary files are removed on every error path.
- FFmpeg in the media worker uses `-protocol_whitelist file,pipe` and a container-format whitelist.
- Library items (music, logos, B-roll) are used in edits only after the owner confirms the rights.
- **Public downloads (yt-dlp)** run in the media worker (no secrets). Only the YouTube and
  Instagram extractors are loaded, so a link can't make yt-dlp fetch other hosts; no cookies,
  credentials, netrc, location faking, impersonation or remote code; size and duration limits
  apply during the download. YouTube's challenge script runs in Deno, which yt-dlp starts without
  file, network or environment permissions.
- **Watched folders:** paths are resolved inside the inbox root only (`..`, `~` and symlinks that
  leave it are refused; symlinks are never followed while scanning), files are copied — never
  opened in place — and validated like uploads; CLIPFORGE writes to the folder only if the owner
  asks it to move finished videos to `Processed`.

## Deployment hardening

- Containers run as an unprivileged user (uid 10001) under `tini`; files created by CLIPFORGE are
  readable only by its service accounts (umask 007: owner and the `clipforge` group).
- Only Caddy is published (plus UDP ports for authenticated SRT live ingest, each session with its
  own passphrase). The API, database and Valkey are reachable only inside the Compose network.
- Use HTTPS for anything beyond `localhost` (`./scripts/install.sh --domain …`).
- Back up regularly and copy backups off the server; backups contain encrypted credentials
  but never the master key.

### Windows installer

- Runs elevated once (to turn on WSL 2); everything else runs as the user. CLIPFORGE lives in its
  own WSL 2 environment, separate from other Linux environments on the PC.
- The Ubuntu image is downloaded over HTTPS and its SHA-256 is pinned in the script; a fallback
  WSL package is installed only if Windows confirms Microsoft's Authenticode signature. Docker
  Engine comes from Docker's signed apt repository.
- `.env` (master key, database password) is created inside the WSL environment with mode 600 and
  is kept on updates. The installer never stores passwords or tokens on the Windows side.

## Controls for automation

Settings → Automation & safety: **pause** (nothing new starts), **emergency stop** (cancels all
jobs, blocks external AI and publishing until cleared), per-integration switches (publishing per
platform, fetching per source, each AI provider), publishing policy (approval required / automatic
/ drafts only), daily publishing limits, AI budgets. The chat accepts the same commands
("pause everything", "hold off posting", "emergency stop") for admins.

## Verification

Automated tests cover encryption binding and rotation, the media worker's inability to read
secrets, SSRF blocking (private ranges, metadata IPs, redirects, DNS pinning), untrusted-text
fencing, CSRF, roles, lockout, session cookie flags, security headers, forged forwarded headers,
upload validation and integration switches — see [TEST_RESULTS.md](TEST_RESULTS.md). Dependency
audit results are recorded there as well.
